## macOS controller verified

Picked up from the resume status; the Xbox Series controller was attached to this Mac over USB (Microsoft 045e:0b12), so the open macOS controller item could be tested for real.

### What the system reports

- `hidutil list` shows `XboxSeriesXGamepad` (045e:0b12, USB, usage page 1 / usage 5).
- The HID device is owned by Apple's DriverKit driver `com.apple.gamecontroller.driver.XboxGamepad`; `InputReportCount` grows between samples, so reports stream.
- `tools/verify_controller.sh` still prints `GameControllerSupportedHIDDevice = No`, but that property is misleading: a GameController probe that pumps the main run loop sees the pad as an extended gamepad and receives live values.

### Probe results

- A CLI GameController probe (`/tmp/mb_gc_live.m`, pumps `CFRunLoopRunInMode` for 0.01 s per turn) reports `count=1`, `extPad=yes`, and live input: A pressed, left stick x reaching 1.00, RT at 1.00.
- A combined probe (`/tmp/mb_pad_capture.m`) also captured raw IOHID reports: report id 32, 19 bytes, values changing with the sticks and triggers. The raw path works too, but the framework path is enough.
- The game's own pump with a 0.0 s timeout does not populate the controller list in a tight loop (count=0); with the game's 60 Hz pacing, the main queue gets its turn between frames, and the real game reads the pad.

### Game verification

Ran the release build with `MB_PAD_LOG=1 MB_START=1.1` and pressed the pad. Logged, in order:

- `controller: Controller` on connect.
- Left stick full range (`Vec2(-1.00, -0.08)` to `Vec2(1.00, 0.02)`), right stick full range (`Vec2(0.99, 0.15)` to `Vec2(-1.00, 0.00)`).
- `A`, `B`, `X`, `Y`, `LeftBumper`, `RightBumper`, `LeftTrigger`, `RightTrigger`, `Start`, `View`, and all four D-pad directions (`Up`/`Down`/`Left`/`Right`).

So the whole `src/pad.rs` macOS mapping reaches the game; the earlier "every value reads zero" was a stale reading (sleeping pad / un-pumped run loop), not a driver or code bug. No code change was needed.

## Stage carry-over and stick menu navigation

Reported by the player: score and upgrades did not carry into the next round, and the left stick did not navigate menus (only the D-pad did).

### Carry-over

- Found the bug: `Action::NextStage` built a fresh `Play::new`, resetting score, rings, upgrade points, upgrades, lives, bombs and multiplier.
- Fixed: `Play::advance_stage` now mirrors `GameScreen::handleEvent`'s next-stage case. The stage starts in the same screen (`WaveManager::startStage`), the run's score, rings, upgrade points, upgrades, lives, bombs and multiplier stay, the boost recharges (`Ship::resetBoost`), and the bought weapon levels and selected weapon are applied to the new ship (`Ship::loadWeaponStateFromGlobal`). Only stage state (script, field, camera, scroll, pickups, timers, enter animation) restarts.
- Verified with `MB_START=1.1 MB_WAVE=99 MB_AUTOFIRE=1 MB_FPS=60 MB_AUTONEXT=1 MB_BUY=0`: the log shows cumulative score (15000, 45000, 90000, 165000, 255000, ... 3945000) and cannon upgrades [1, 2, 3, 4, 5, 6, 7, 7, ...] carried across 30 stage advances; rings, upgrade points and lives were kept too. `MB_AUTONEXT` skips the results/upgrade popups for scripted runs; `MB_BUY=<index>` buys one upgrade first.
